## 二、完整功能展示流程

### 1. 项目介绍（约 40 秒）

**页面操作：** 停留在登录页面或系统首页。

**讲解词：**

> 大家好，我们的项目叫 IssueScope，是一个面向 GitHub 开源项目维护者和开发团队的仓库理解与 Issue 智能分析平台。
>
> 在传统维护流程中，开发者需要分别查看代码、README、Issue、Pull Request 和提交记录，理解项目和定位问题的成本比较高。IssueScope 将这些信息统一同步到一个工作台，并结合规则分析、知识检索和大模型工具调用，帮助维护者快速理解项目、分析 Issue，并生成处理建议。

### 2. 登录和用户体系（约 40 秒）

**页面操作：** 使用管理员账号登录。

**讲解词：**

> 系统首先提供了完整的用户认证功能，包括注册、登录和身份保持。密码不会以明文保存，而是经过哈希处理后存入数据库。
>
> 系统还区分管理员和普通用户。管理员可以管理用户，普通用户只能维护自己的模型和 GitHub 配置，实现多用户配置隔离。

### 3. 仓库接入与概览（约 1 分 30 秒）

**页面操作：**

1. 进入“仓库概览”。
2. 选择已有的 `S1mpleWind/wgy666`。
3. 展示语言、文件、Issue、Pull Request 和提交统计。
4. 打开文件列表或 README。

**讲解词：**

> 这是仓库工作台。系统支持输入公开 GitHub 仓库地址进行同步。
>
> 同步过程中，后端会获取仓库基本信息、语言分布、目录树、README、Issue、Pull Request 和近期提交。同时还会克隆代码，建立文件索引，并将结果持久化到 PostgreSQL。
>
> 为了保证现场展示稳定，我现在使用的是已经同步并缓存到数据库中的仓库。这里可以看到仓库的语言分布、文件规模、Issue 数量和近期活动。
>
> 系统不仅保存 GitHub 返回的概览信息，还会保存可用源码内容，供后续项目解析、仓库问答和 Issue 定位使用。

如果老师要求现场同步，可以补充：

> 公开仓库即使不配置 Token 也可以同步；配置 GitHub Token 后，可以提高 GitHub API 的访问限额。

### 4. 项目结构解析（约 2 分钟）

**页面操作：**

1. 点击左侧“项目解析”。
2. 展示架构图。
3. 点击“主要目录”“依赖文件”或“入口文件”。
4. 展示“架构健康检查”或“变更影响”。

**讲解词：**

> 接下来是项目结构解析。这里主要使用确定性规则，而不是完全依赖大模型。
>
> 系统会识别源码模块、主要目录、依赖配置、入口文件、测试、文档和 CI/CD 文件，并生成项目结构视图。
>
> 使用规则解析的好处是结果稳定、速度快，而且容易追溯。大模型主要用于需要语义理解的问答和 Issue 处理，两者各自负责适合的部分。
>
> 在架构视图中，系统还会分析模块和文件之间的关系。变更影响功能可以从某个文件或 Issue 描述出发，沿导入、调用和测试关系查找可能受影响的文件、接口以及建议执行的回归测试。
>
> 架构健康检查则关注循环依赖、模块耦合、超大文件、测试映射和解析覆盖率等指标。

建议只重点展示“架构图”和“健康检查”两个页面，不要逐个打开所有页面。

### 5. Issue 智能分析（约 1 分 30 秒）

**页面操作：**

1. 点击“Issue 智能分析”。
2. 展示 Issue 处理流水线。
3. 打开一条已有分类结果的 Issue。
4. 展示分类、置信度、分析理由和识别信号。
5. 打开通知列表，展示 Webhook 事件。

**讲解词：**

> IssueScope 会对同步到的 Issue 进行自动分类，目前支持缺陷、功能请求、使用咨询、文档问题、重复问题和信息不足等类别。
>
> 分类流程采用“大模型优先、规则兜底”的方式。如果模型不可用，系统仍然可以通过关键词和标签规则完成基础分类。
>
> 页面不仅显示分类结果，还显示置信度、分析理由和识别信号，避免只给出一个没有依据的标签。
>
> 系统还支持 GitHub Webhook。当仓库出现新 Issue 时，GitHub 可以把事件主动推送到后端，系统完成分类后在通知中心展示。
>
> 对咨询类 Issue，系统可以生成回复草稿；对 Bug 类 Issue，还可以定位代码并生成修复候选。所有外部写操作都需要用户再次确认。

现场不要点击“确认回复”或“确认修复并提 PR”。可以解释：

> 自动回复和自动修复会真实修改 GitHub，所以现场环境没有配置写权限 Token。正式使用时，修复会提交到独立分支并创建 Pull Request，不会直接修改主分支。

### 6. 仓库智能问答（约 1 分 30 秒）

**页面操作：**

1. 点击“仓库问答”。
2. 输入提前测试过的问题。
3. 展示回答下方的工具调用和文件引用。
4. 点击一个引用，打开源码弹窗。

推荐问题：

```text
项目的后端入口文件在哪里？请给出引用。
```

备用问题：

```text
用户登录请求会经过哪些后端模块？
```

**讲解词：**

> 这是仓库智能问答功能。它和普通聊天机器人的区别是，回答前会加载当前仓库上下文，并自主调用文件搜索、README 检索和知识图谱等工具。
>
> 比如我询问项目入口的位置，系统会先检索仓库，再根据工具结果生成回答。
>
> 回答下方会展示调用过的工具和引用文件。点击引用可以直接查看源码，也可以跳转到 GitHub 对应位置。
>
> 这种设计提高了回答的可追溯性，降低了模型脱离代码仓库进行猜测的风险。

现场只问一个提前验证过的问题，避免模型服务响应时间影响展示节奏。

### 7. FAQ 知识库（约 50 秒）

当前服务器 FAQ 为空，建议展示前手动准备一条：

```text
问题：如何配置 GitHub Token？
回答：进入用户管理，在“我的问答与 GitHub 配置”中填写 GitHub Token 并保存。
```

**页面操作：**

1. 点击“FAQ 知识库”。
2. 展示新增、编辑、确认和删除入口。
3. 不建议现场点击“自动生成”，避免等待模型。

**讲解词：**

> 对于高频问题，如果每次都调用大模型，会增加延迟和成本。因此系统提供了 FAQ 知识库。
>
> FAQ 可以手动维护，也可以从相似的历史 Issue 中自动生成候选内容。自动生成的条目需要人工确认后才会正式生效。
>
> 新 Issue 到达时，系统会优先匹配 FAQ。命中后可以直接使用已有答案，不必再次调用大模型。

### 8. 用户管理和集成配置（约 1 分钟）

**页面操作：**

1. 点击“用户管理”。
2. 展示集成连接状态。
3. 展示 API 请求和 Token 用量。
4. 展示用户列表，但不要编辑或删除。

**讲解词：**

> 最后是用户与配置管理。每个用户可以独立配置自己的模型地址、模型名称、API Key 和 GitHub Token。
>
> 密钥不会在接口响应或页面中重新显示，留空保存也不会覆盖已有密钥。
>
> 系统还会记录当前用户的 LLM 请求次数、GitHub 请求次数，以及模型返回的 Token 用量，便于后续进行额度和成本管理。
>
> 管理员可以查看和维护用户资料，而普通用户没有这部分管理权限。

### 9. 总结（约 30 秒）

**讲解词：**

> 总结来说，IssueScope 打通了从仓库同步、结构解析、Issue 分类、仓库问答、Webhook 监听到 FAQ 和自动修复的完整流程。
>
> 系统的设计重点不是让大模型替代所有规则，而是让规则负责稳定的结构分析，让大模型负责复杂语义理解，并通过工具调用、源码引用和人工确认保证结果可追溯、外部操作可控制。
>
> 以上就是我们的功能展示，谢谢大家。

## 四、现场故障预案

### 仓库数据加载失败

> 当前 GitHub 网络存在波动，我展示一下已经缓存的仓库数据。系统支持数据库持久化，不需要每次从 GitHub 重新同步。

### 仓库问答失败

> 问答依赖外部模型服务。系统已经提供规则分析和缓存检索降级，项目概览、结构解析和 Issue 基础分类仍然可以正常工作。

### 模型回答太慢

> 系统正在执行仓库工具调用。与普通聊天不同，它需要先读取项目上下文，以确保答案能够提供文件依据。

### 自动回复或自动修复不能使用

> 这两个功能会真实写入 GitHub，需要配置具有仓库权限的 Token。为了避免展示环境误操作，我们这里只展示分析结果和确认入口。

### 架构演化页面没有对比结果

> 精确架构差异需要至少两个不同提交的完整架构快照。当前服务器只有一个快照，所以这里展示的是提交时间线和单版本架构分析。

## 五、常见提问与回答

### 为什么不用纯大模型？

> 目录、依赖、入口和调用关系更适合确定性解析。大模型主要负责语义问答和回复生成，这样结果更稳定、成本也更低。

### 怎么减少模型幻觉？

> 回答前调用仓库工具，回答后返回源码引用，同时保留工具调用记录。关键外部操作还需要人工确认。

### 自动修复会不会直接破坏代码？

> 不会。系统会创建独立分支、提交修改并发起 Pull Request，不直接修改主分支。

### 模型不可用怎么办？

> Issue 分类有规则兜底；Embedding 有远程、本地模型和哈希检索三级降级；仓库概览和结构解析不依赖大模型。

### 数据存在哪里？

> 仓库快照、源码索引、Issue、Webhook、FAQ、用户配置和知识图谱保存在 PostgreSQL 中，向量检索使用 pgvector。
